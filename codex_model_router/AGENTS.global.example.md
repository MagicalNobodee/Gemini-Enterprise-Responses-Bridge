# Codex 通用模型分流与多代理协作指示模板

> 使用说明：
> 1. 若要在新电脑上让 Codex 自动完成“多供应商模型分流”搭建，可将 **第一部分** 直接发给 Codex 执行。
> 2. 若要规范日常多模型协作与子代理（Subagent）分工，可将 **第二部分** 按需复制到本机 `~/.codex/AGENTS.md`（切勿写入任何私人密钥或令牌）。

---

## 第一部分：给 AI 助手的模型分流搭建与维护指示

当需要为本机 Codex 配置或更新多供应商同菜单模型分流时，请遵循以下通用规范：

1. **先备份、零泄密**：修改 `~/.codex/config.toml` 或 `~/.codex/model-router/` 前，必须先建立仅当前用户可读（`0600`）的时间戳备份；严禁在终端输出、日志、提交记录或回复中打印任何上游 API Key、Bearer Token 或私有网关密钥。
2. **统一本地分流入口**：将 Codex 当前 `model_provider` 的 `base_url` 与 `model_catalog_url` 指向本机分流器（默认 `http://127.0.0.1:18001/v1` 及 `/v1/models`），并保持原供应商的认证配置在 `config.toml` 中原封不动。
3. **按规则而非硬编码分流**：在 `~/.codex/model-router/settings.json` 的 `routes` 中按用户实际拥有的模型 ID 或通配符前缀（如 `gemini-*`、指定模型列表或其他本地/远程兼容端点）配置转发规则：
   - 发往本地无密钥网关（如 `http://127.0.0.1:8000/v1`）的路由，必须开启 `strip_auth: true` 自动剥离原供应商认证头，防止密钥跨上游泄露；
   - 对不支持 OpenAI 托管搜索的目标路由开启 `strip_hosted_web_search: true`，同时完整保留本地函数与 MCP 工具。
4. **合并模型目录快照**：将原供应商的模型列表与新增路由的模型条目合并写入 `~/.codex/model-router/models.json`（可通过 `codex_model_router/install_router.py --catalog-models <模型列表> --route-models <匹配规则> --apply` 自动生成），使所有模型在同一 Codex 下拉菜单与子代理模型列表中同时可见。
5. **闭环验收**：配置完成后，必须实际检查 `/health`、`/v1/models` 以及分流单元测试（验证目标模型走新路由且不带原密钥、其余模型走默认上游且保留原认证）。

## 第二部分：日常全局协作与子代理调度指示（可放入 `~/.codex/AGENTS.md`）

### 多会话并行协作规则

- 同一工作区可能同时运行多个 Codex 会话并行修改代码。工作区存在未提交改动或文件在排查期间被其他会话更新属于正常状态，不要因检测到外部改动而机械停工询问。
- **局部精准合入（先读最新、只改局部）**：每次修改文件前，先读取目标位置的最新片段；用 `apply_patch` 只修改本任务涉及的代码块，绝不整文件覆盖或回滚其他会话的改动。
- **共享服务重启前先查状态**：运行测试优先使用独立单测或临时端口；重启本机常驻网关（如 `8000`）或分流器（如 `18001`）前，先检查服务状态确认没有正在执行或排队的请求。
- **唯一停下询问的例外**：仅当确认另一活跃会话正在重写同一文件的同一段核心逻辑且改动方向直接冲突时，才简短说明冲突点并询问。

### 按需使用子代理（Subagent）与跨模型分流协同

- 主会话担任总控（Coordinator），负责理解需求、拆解任务、分派子代理、整合结果、运行测试验证并统一汇报。
- 根据任务规模和独立模块数量自行判断是否创建子代理：简单任务直接完成；存在多个写入范围互不重叠的子任务或独立核查任务时，主动并行派发子代理。
- 子代理默认继承主会话当前所选模型；启用本机模型分流器后，仅在用户明确指定模型名称时按需传入 `model` 覆盖参数，交由分流器自动路由至对应上游。
- 收到子代理结果后，总控必须亲自审查改动并运行验证，确认无误后再交付。
